# Continuous mission — non-finite engine execution boundary

**Status: PARTIAL.** This is a defensive execution-boundary change, not a complete numerical safety case or a field-validation finding.

## Reproduction and control

Before this change, `EngineRegistry.execute("drilling.mse", ...)` accepted positive infinity as `wob_si` and returned `mse_si=inf`. An HTTP result containing this value cannot be represented as strict JSON and the engine service could try to hash or persist it. A second reproduction used finite `wob_si=1e308`, `torque_si=2650`, `rpm_si=96`, `rop_si=18` and `bit_diameter_si=0.2032`: floating-point calculations produced non-finite output. These are adversarial software tests, not physically meaningful engineering input.

The registry now rejects non-finite floats in nested JSON-like input and typed models before validation, and again after Pydantic coercion; it rejects non-finite values anywhere in the returned result envelope. A rejected input uses `engine.input_invalid` and a rejected result uses `engine.convergence_failed`, both HTTP 422. The error contains the engine key, not the rejected numerical value. Input is checked before model validation because validation errors can otherwise echo non-finite raw values into an error response. The normal service invokes the registry before hashing or persisting an engine run; API tests verify no run is created for the tested failures. No value is silently replaced with zero, null or a bounded number.

The test suite exercises raw infinities and NaN, string coercion, nested survey input, `model_construct` inputs, a fabricated nested result, the real finite-input MSE overflow and JSON-serializable API responses. One initial test used an incorrect expected error code; it failed, was corrected to the existing `engine.convergence_failed` contract, and the focused tests subsequently passed. The internal `fluids._reynolds` infinity sentinel is not globally prohibited: only input/output at the registry boundary is inspected. Normal engine regression tests cover the default usage, not all possible hydraulic cases.

## Boundaries and remaining work

This guard only inspects Python floats in Pydantic model fields and nested built-in containers at the registry boundary. Direct calls to calculation functions, third-party numeric types, unusual custom serializers, intermediate overflow that later yields a finite result, underflow, arithmetic exceptions, unrealistic but finite values, numerical stability and incorrect equations are not certified. In follow-up registry probes, otherwise finite MSE inputs with bit diameter `1e-300` raised `ZeroDivisionError` after underflow, and diameter `1e308` raised `OverflowError`; neither reached the result guard. These adversarial diameters are not physically meaningful and this is not a claim about realistic operating ranges. No successful result was returned in those probes. A subsequent [MSE-specific numerical guard](CONTINUOUS-MSE-NUMERICAL-FAIL-CLOSED.md) handles these tested cases; domain limits and other engines still require separate review. It does not define physical operating limits, repair historical records, validate all paths outside the registry, or prove that every arithmetic failure yields HTTP 422. The complete per-engine independent equation, unit, range and sensitivity audit remains outstanding. `well_control.kill_sheet` and `tubulars.api_5c3` remain `NEEDS_FIELD_VALIDATION`.
