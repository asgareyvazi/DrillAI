## Purpose and assurance rules

This is the source-based starting assessment and the live execution record for CP76–CP112, not a production-readiness certificate. The 19 area assessments below were made against the checked-out source before CP76 changed product code; the CP76–CP97 entries remain historical checkpoints, not current-SHA verification. Each later completion entry must name the actual source, tests, and evidence, and must retain unavailable evidence as a residual.

A capability is not complete merely because a table, endpoint, screen, or test exists. Reassess each affected feature across the typed data model and database constraints; API/service validation and transactions; server-side authorization and tenant scope; usable English/Persian UI with correct RTL/LTR; optimistic concurrency, revisions and audit; time/depth/unit/evidence provenance; failure and recovery behavior; meaningful automated tests, including real browser acceptance where relevant; and matching operator documentation. Do not infer OCR or LLM quality, vendor interoperability, message delivery, field/engineering acceptance, user acceptance, or production recovery from deterministic software tests.

Standing safety limits:

- `backend/src/drillai/engines/registry.py` is the authoritative engine inventory. `well_control.kill_sheet` and `tubulars.api_5c3` remain `needs_field_validation` without genuine field evidence.
- Do not infer survey datum, vertical reference, or azimuth compatibility, and do not silently transform unknown or magnetic azimuths.
- Ingestion/creation time is not observed event time. A lone `period_end` is not an event. Preserve explicit time/depth basis and unknown states.
- A local adapter/harness is not external-vendor traffic; a queued or provider-accepted notification is not a delivery receipt; a synthetic benchmark is not real-corpus quality or field acceptance.
- Keep all Arena-facing communication, commits, and documents in English; preserve English/Persian and LTR/RTL product behavior.

- **Present—reverify** — implementation exists, but this mission must inspect and test it at the relevant current/final SHA.
- **Partial—evidence bounded** — useful implementation exists, while a defined capability or independent evidence remains absent.

## Domain and data-governance questions carried into CP77

The following are design-review questions, not assumptions already settled by source presence:

1. Which concepts require authoritative typed columns/tables, immutable source evidence, referential integrity, tenant-consistent relationships, uniqueness and deletion/retention policy?
2. How are report identity, report date/shift/timezone, revision, reissue/correction, status, author/reviewer/approver, and optimistic concurrency represented without mutating accepted history?
3. For each activity, measurement, event and survey value: what is the observed/reported/calculated/planned/inferred/unknown basis, source record/document/page/region, observed event-time basis, original unit/value, canonical unit/value, depth reference, and confidence/review state?
4. Which fields may be corrected manually, which imported values remain immutable evidence, how do duplicate/collision detection and idempotency work, and how is a reviewer decision audited?
5. Which relationships are hard foreign keys versus external vendor identifiers, and how are well/wellbore/section/organization consistency and lifecycle deletion protected in both SQLite and PostgreSQL?
6. Which report sections may be profile-defined text or configuration, and which safety-critical engineering measurements require typed models, controlled vocabularies, dimensional/unit validation and explicit provenance rather than arbitrary JSON?
7. What are the source-of-truth and reconciliation rules between a report revision, promoted operations/events, telemetry, the twin, analytics and export snapshots?
8. What retention, legal hold, redaction, authorization, audit immutability, secret separation and export privacy rules apply to report attachments and recipient data?
