# CP136 — DDR Intake, Review, and Database Readback

**Status:** implementation plus focused and full local software verification are complete. This report does not claim exact-SHA Linux/native-Windows certification; CP151 owns the fresh final-SHA matrix.

## Implemented

CP136 strengthens the daily-report lifecycle journey so the browser exercises the real operator path instead of creating the uploaded source through a test-only API shortcut:

1. A synthetic project, well, and wellbore are created through the product API. The browser opens the well's Documents workspace, selects the engineer role and DDR document type, chooses the wellbore, and uploads a generated CSV through the real file input. The browser observes the actual `POST /api/v1/documents` response and requires HTTP 201.
2. The test reads the persisted document through the API and waits for the real extractor to create a `report_header` and an `operation_row`. It checks the uploaded document's well/wellbore scope and the extracted date, report number, summary, operation, duration, and explicit measured-depth value.
3. Through the Daily Reports workspace, the operator selects the exact header and operation records, maps the report date/number and summary to source fields, supplies the explicit wellbore and time zone, and reviews five provenance-linked reconciliation proposals. The user accepts each proposal, submits the draft, then switches to a distinct drilling-supervisor principal to approve it. API readback confirms the submitted/approved states and actor separation.
4. A separate Python helper opens the same E2E SQLite database read-only and verifies the stored report identity, approved revision pointer, source document/record IDs, accepted reconciliation rows, typed duration source value/unit, and source/accepted measurement values/units. Free-text summary/activity fields are emitted only as SHA-256 digests; no transcript or path is printed.
5. The operator creates a correction from the approved revision. API readback verifies a new draft with `supersedes_revision_id` and preserved source links; the existing approved-revision pointer remains at revision 1, while all five reconciliation proposals in revision 2 restart as `proposed`. The browser then reads revision 2 and explicitly selects historical revision 1 from the same SQLite database, checking that the older approved data remains intact and that neither read changes the report's latest pointers. API history contains both immutable revisions.

The helper accepts only an absolute `sqlite+aiosqlite` URL with no query/fragment and a resolved `.e2e` or `.e2e-*` parent containing `e2e.db`. It resolves symlinks before that check, connects using SQLite `mode=ro`, sets `PRAGMA query_only=ON`, uses parameterized queries and scopes reads by report, well, wellbore, and the report's organization. The optional revision selector accepts only positive, non-boolean integers and rejects numbers beyond the current latest revision; omitting it preserves latest-revision behavior. Database/SQL errors and command arguments are not echoed into the browser output. The focused helper tests verify latest and historical snapshots, hashes-only output, unchanged database digest, read-only write refusal, invalid revision/path/URL inputs, and cross-well/wellbore refusal.

## Limits and acceptance boundary

It is not an exact-SHA CI result, a real operator/customer approval, field-document interpretation evidence, OCR quality acceptance, a vendor/provider response, or production readiness.
