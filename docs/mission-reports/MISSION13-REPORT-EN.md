## Security finding and verification limits

A subsequent ordered focused run (CP17, CP31, then CP24 security) produced **11 passed and 1 failed**: an app created with `auth_enabled=True` returned HTTP 200 instead of 401 for an unauthenticated wells request. CP31 had populated the process-wide cached settings with auth disabled; `current_auth` reads those global settings rather than the app's explicit settings. The CP24 test passed when run alone, so the successful full-suite result does not rule out this order-dependent configuration mismatch. This is a potential authentication bypass when applications with differing settings share a process or cached settings disagree with the factory arguments; it remains **NOT_ACCEPTED**, not fixed. The post-change CI guard subset passed **8 tests**; the Linux provenance shell was separately checked with matching, mismatched and absent SHA (exit 0, 1 and 1). The full regression above preceded the final CI-shell guard correction and its test update.
