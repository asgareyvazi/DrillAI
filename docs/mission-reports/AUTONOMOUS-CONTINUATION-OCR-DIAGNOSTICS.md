## New instrumentation

The existing synthetic benchmark now aggregates, separately for English and Persian, counts of expected fixed labels found anywhere in normalized page text, expected labels found as normalized colon-delimited prefixes, reversed-character label hits, and pages containing bidi control characters. Only numbers are retained; recognized text, expected field values, source images and individual token contents are not emitted. The reversed-character test is merely a heuristic, not proof of a particular RTL failure. Bounded, type-checked counters are exposed in the existing GitHub diagnostic annotations. This can help distinguish absent labels from label-position effects in a future deployment-image run without retaining transcripts. The unchanged score and failure gate remain authoritative. A focused test verifies the counts, annotation safety and rejection of untrusted values; it does not establish OCR accuracy. Diagnostics can be incomplete if processing fails, and their evaluated counts must be consulted.

This narrowly scoped source comparison does not establish whole-runtime equivalence or a root cause. A concrete synthetic-rendering defect explains an important part of the deployment/local discrepancy. The corpus renderer already uses `arabic_reshaper` and `python-bidi` to produce visual-order Persian strings, then Pillow's default font engine may silently choose RAQM and reorder those strings a second time. Local FriBidi 1.0.16 made Pillow 13.0.0 RAQM available; the same synthetic case 033 PDF SHA-256 became `de346c6cbc5f8d8729f7c45a2c640c4e2e5dea0f7d0fa5dae718e11c1d472863`, exactly the case 033 SHA printed in the deployment run's annotation. Without RAQM it was `b1a7ce7fd3a1f7296022475fddf66c7844c61c1dfc83943f6707fde3245d26f0`. In the separate local Tesserocr 5.5.4 CLI-protocol emulator using the same traineddata hashes, RAQM-enabled pre-fix rendering evaluated 64/64 with CER 0.317870, WER 0.460911, Persian 0/192 and 25 reverse-label hits. This is a strong controlled reproduction of the rendering mechanism, not a deployment CLI execution or proof that no other differences exist. [Pre-fix synthetic report](MASTER-RTL-RAQM-REPRODUCTION-f29.json), SHA-256 `201c192184ba554574d5b32e8a354c88b9994e4b7bca591c188c8239db96fc68`.

The fixture renderer now explicitly requests Pillow BASIC layout for every font; already-shaped visual text is no longer reprocessed. The renderer policy is versioned v4. Neither the corpus bytes, truth, scoring, thresholds, cases nor selection changed. With and without RAQM, case 001, 033 and 050 synthetic PDF hashes match exactly in this environment. This corrects malformed synthetic inputs; it is **not** itself a repair of OCR on real documents, and historical CI results must not be relabelled. On the same local emulator with RAQM available, the corrected 64-case renderer produced CER 0.107024, WER 0.154639, critical 311/384; Persian CER 0.227241, WER 0.296769, critical 121/192. This still fails acceptance, particularly Persian and strata. [Corrected synthetic report](MASTER-RTL-BASIC-CORRECTION-f29.json), SHA-256 `d6effa436c537df706268c4f60730514200ce3acafd1cf5c133ff33124a202a5`. No holdout or real-document accuracy was established.

An independent real ingestion defect was also reproduced and corrected: Tesseract's `GetTSVText` emits raw symbol text rather than CSV-escaped fields, but Python's default CSV quote parser treated a leading literal quote as an opening quote and swallowed the next source row into the first line and bounding box. The production parser now treats quotes literally, rejects ambiguous extra columns instead of silently attaching a truncated word, and increments the adapter version to v8. The regression verifies literal quotes, distinct line boxes, confidence, and downstream PDFium parsed page/region provenance using a synthetic provider; it does not assert that Tesseract recognition is accurate or that these quotes caused the Persian failure. The quality verifier requires the new adapter and renderer policy; its thresholds remain unchanged.
