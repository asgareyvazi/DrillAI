## CP113 forensic findings

### Architecture and registered surfaces

- **Frontend:** React/TypeScript/Vite, one route/navigation inventory in `frontend/src/App.tsx` and `frontend/src/components/layout/AppShell.tsx`, TanStack Query API clients, shared bilingual English/Persian catalogue, and well-scoped workspaces under `frontend/src/pages/wells` and `frontend/src/pages/engineering`.
- **API/domain:** FastAPI routers in `backend/src/drillai/api/routers`; tenant-scoped dependencies and action authorization in `api/deps.py` and `security`; domain services under `assets`, `documents`, `drilling`, `operations`, `telemetry`, `workflow`, and `twin`.
- **Persistence:** SQLAlchemy models under `backend/src/drillai/db/models`, 26 ordered Alembic revisions, content-addressed raw document storage through `ingestion/storage.py`, and explicit source/evidence records. There are separate SQLite, PostgreSQL, migration, concurrency, and authorization test groupings.
- **Engineering:** the engine registry imports eleven shipped domain modules; `trajectory.minimum_curvature` is typed, versioned, stores canonical SI values, declares azimuth-frame identity and correction requirements, and has analytic/reference-style tests. `execute_engine` persists canonical inputs/outputs and hashes in `EngineRun`.
- **Document/OCR/RAG/AI:** document upload persists a `RawArtifact` and runs PDF/DOCX/XLSX/CSV/text ingestion; extractors retain row/page/region evidence and review state. OCR has a runtime probe and a pinned-manifest CER/WER benchmark. Retrieval supports lexical/vector/hybrid modes, but only a small lexical smoke benchmark is checked in. Advisor answers are structured into facts/calculations/evidence/unknown; Echo is deterministic and the OpenAI-compatible adapter is configurable.
- **Operations/telemetry/workflow:** operations/events/NPT/timeline and DDR are persisted services; read-only WITSML/ETP connectors use bounded workers, checkpoint/fencing and an egress policy; workflow execution is persisted; notification adapters record transport acceptance separately from recipient delivery.
- **Deployment:** Compose defines PostgreSQL, migration, backend, connector worker, and Nginx frontend with health checks; the Linux CI Compose smoke checks the proxied deployment. Backup/restore tooling and PostgreSQL drills exist, but no production-like recovery objective is claimed.

### Confirmed partial/disconnected user flows

1. **Survey/Trajectory is the largest product gap.** `SurveyTableExtractor` recognizes survey tables; uploaded `survey_report` documents may create `survey_station` extracted records; `documents.py` permits validated survey metadata corrections; `Trajectory` and `TrajectoryStation` store versioned calculated rows; `DdrProcessor` can promote report-derived survey rows; and the minimum-curvature engine is registered. However, there is no dedicated survey route, navigation item, typed survey API, manual survey editor, revision-comparison workflow, chart/table workbench, or direct survey export. The generic JSON engine runner and document review page do not complete that workflow. This is repository-feasible and is the priority of CP115.
2. **Engineering calculations are usable but mostly registry-driven.** The generic `/wells/:wellId/engineering` page can run registered engines with a typed engine catalogue, unit contract, history and evidence. It is not a replacement for domain-specific workbenches; survey is a concrete example. The safety-sensitive kill-sheet and API 5C3 tools still require field validation.
3. **DDR is substantially first-class in software.** The manual and document-backed routes converge on `DailyReportService`; numbered immutable revisions, reconciliation, CAS, source links, submit/review/correction/export, audit, and tenant/scope constraints are persisted; `DailyReportsWorkspace` and the daily-report Playwright spec exercise synthetic flows. Real source correctness and operator acceptance remain external/field evidence, not software completion.
4. **Document extraction is a proposal pipeline, not automatic truth.** Upload→content-addressed artifact→parser/page/region→extractor→review API→promotion/reconciliation is wired. An extracted value remains unapproved until reviewed; unsupported or ambiguous data still needs an explicit review path and real-corpus evaluation.
5. **OCR runtime readiness and OCR quality are separate.** `ocr_runtime.py` reports Tesseract, configured language and PDFium availability and has a synthetic non-empty-text canary. `ocr_benchmark.py` requires operator-governed, hash-pinned corpus and gold text and measures CER/WER. No approved real corpus or field accuracy result exists. The actual deployment image's OCR runtime still needs a dedicated smoke/evaluation gate.
6. **RAG evidence is honest but under-sized.** `rag/retriever.py` supports several retrieval modes and scope guards; the committed benchmark in `rag/benchmark.py` contains **5 chunks and 3 questions**, requests lexical retrieval only, and does not measure semantic quality, prompt-injection resistance as a benchmark dimension, or realistic multilingual generalization. The current benchmark is smoke evidence only.
7. **Advisor provider path is real code but live evaluation is not evidence.** `OpenAICompatibleProvider` and the provider registry allow configuration, while Echo supports deterministic offline tests. No provider credentials or live response were independently verified. Source-backed structured facts/calculations and abstention are still the authoritative contract.
8. **Connector tests are local harness evidence.** WITSML 1.4.1.1/ETP 1.2 protocol harnesses, SSRF/egress checks, worker checkpoint/fencing and the optional external interop runner are present. No guessed endpoint or external vendor call was made; external commissioning remains `BLOCKED_EXTERNAL`.
9. **Notification status means transport acceptance, not delivery.** Webhook/SMTP/in-app outbox, retry/dead-letter/reconciliation-required states and a platform panel exist. The in-app adapter has no recipient inbox/read receipt, and webhook/SMTP acceptance is not an end-recipient receipt.
10. **Security evidence is repository adversarial testing, not an external assessment.** Auth/RBAC, tenant-scoped services and composite database constraints have dedicated tests. Do not describe these as an independent penetration test or qualified security certification.

### Cross-cutting review risks

- Some business facts exist in both extracted-record payloads and typed domain tables. Promotion and reconciliation must remain explicit and source-linked; no second implicit “truth” should be introduced.
- The survey extractor, document-review validation, trajectory engine, and trajectory persistence currently meet at separate contracts; there is no single user-visible typed bridge, and there is no source-revision comparison API. CP115/116 should use the current trajectory engine/unit contract and existing `Trajectory` persistence rather than add a parallel JSON-only store.
- E2E inventory shape is not browser execution. For CP112, actual execution was established by the exact run; for new work, only exact-SHA browser steps count.
- Synthetic records and formula tests prove software behavior only. Unknown dates/units/frames, extraction uncertainty, source conflicts, recipient delivery and unverified NPT must remain visibly unresolved.
