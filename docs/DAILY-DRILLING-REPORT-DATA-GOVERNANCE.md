# Daily Drilling Report Domain and Data Governance

**Decision record:** CP77 (2026-11-01)
**Status:** Accepted for implementation on `arena/9d8f5568-drillai`
**Scope:** Daily drilling report (DDR) identity, revision lifecycle, measurement/activity records, import reconciliation, provenance and authorization. This is a domain decision, not field or production acceptance.

## Context

Source review found no first-class DDR entity or revision lifecycle. A DDR is currently a document classification whose extracted records may be promoted into operations, events, trajectories, and twin aspects. That pipeline cannot, by itself, answer which report is authoritative, who corrected a value, what a reviewer accepted, which earlier revision it replaced, or whether an import has converged with a manual report. `ReportingService` builds a transient structured payload and the drilling router exports JSON; neither is a persisted report.

The surrounding platform supplies useful patterns: immutable raw artifacts and document/region provenance; schema-versioned extracted records; tenant-scoped asset resolution; operation/event compare-and-swap and audit; `ChangeRecord` for domain history; `AuditLog` for authorization evidence; and a unit registry that refuses unlabelled or dimensionally invalid measurements. The DDR domain will compose those patterns, not replace their source records.

## Decisions

### 1. Separate logical report identity from report revisions

- A `DailyDrillingReport` is the stable logical identity for one tenant, wellbore, local report date, and normalized identity key. The identity key is the normalized operator report number when supplied, otherwise the shift code; a custom shift also includes its normalized custom label. Database uniqueness prevents duplicate logical reports; request idempotency handles safe retries. A changed source document with the same identity is a conflict to reconcile, never a second silently accepted report.
- The report stores organization, well, and wellbore scope. The well must own the wellbore, all referenced rows must belong to the same organization, and scope disagreement is rejected. New report/source relationships use database foreign keys where the referenced entity is local; service validation still checks tenant and hierarchy because ordinary single-column FKs cannot establish tenant ownership.
- `DailyDrillingReportRevision` holds a monotonic revision number, typed report metadata/content, status, submit/review actors and times, decision reason, edit version, and optional superseded revision. `(report_id, revision_number)` is unique. A correction is a new revision; an approved historical revision is never edited in place.
- Drafts may be edited only through a server service with an expected edit version. Submission freezes the revision. A reviewer may approve or reject with a reason and must be a different principal from the submitter. A correction after rejection or approval forks a new draft from the relevant revision. Approval history remains queryable when a later revision supersedes the earlier one.
- The logical report tracks the latest revision and latest approved revision separately. A draft correction must not make the previously approved revision appear unapproved or erase its audit history.

### 2. Model engineering data as typed records, not an arbitrary JSON payload

- Header fields, operational narrative fields, report identity, timestamps, status, actors and revision numbers are typed columns.
- Activity spans are separate `DailyReportActivity` rows. Their activity/event class is a controlled vocabulary; operation/NPT classifications are validated against existing canonical vocabularies. Start and end instants are independently nullable and each carries an explicit basis. Depth endpoints are numeric SI metres with an explicit depth reference and basis. A reporting-period boundary is never substituted for an activity/event instant.
- Numeric measurements are separate `DailyReportMeasurement` rows with a controlled `parameter_key`, expected dimension, canonical value/unit, exact source numeric value/unit, value basis, optional explicitly based observation time, and optional depth with reference/basis. The service derives the expected dimension/canonical unit from the parameter catalogue and calls `drillai.units.registry.convert`; callers cannot choose an unrelated dimension or claim that an unlabelled number is canonical.
- The initial parameter catalogue is intentionally limited to quantities already supported by the unit engine and a named operational use (measured/hole/bit depth, ROP, WOB, rotary speed, flow rate, standpipe pressure, torque, hookload, mud weight, temperature and funnel-viscosity time). No derived or unsupported quantity is invented to make an import look complete. Extending the catalogue requires a dimension, canonical unit, accepted source units, validation ranges where justified, tests, UI labels and documentation.
- Narrative-only values remain bounded text columns. Unmapped, ambiguous or unsupported extracted values remain linked source evidence for a human reviewer; they are not smuggled into an untyped JSON measurements blob. JSON is reserved for explicitly schema-versioned configuration/evidence metadata, not the report's engineering facts.

### 3. Treat reporting period, event time and ingestion time as different facts

- `report_date` is the local civil date printed/declared by the report; `report_timezone` is an explicit IANA timezone. It is not recomputed from UTC, machine locale or organization defaults.
- Any provided instant must contain an offset and is normalized to UTC for storage. Period start/end are optional, independently sourced reporting-period facts; if both are supplied they must be ordered. No period boundary is used as an activity's start, event time or observation time.
- Each activity endpoint and measurement timestamp is nullable and has a vocabulary such as `observed`, `reported`, `calculated`, `planned`, `inferred`, or `unknown`. Unknown time is represented as no instant plus `unknown`, not a fabricated timestamp. If the source only says the report ends at a time, that remains a period boundary.
- Every depth states its reference (`md`, `tvd`, `tvdss`, or `unknown`) and basis. Unknown datum/reference is preserved and cannot be converted or merged into a referenced trajectory. A single general report depth does not overwrite `well_sections.actual_bottom_md_si`; the established progress source remains unchanged.

### 4. Preserve source lineage and distinguish source evidence from decisions

- An imported report revision names its source `Document`; its report header, activities and measurements may each cite the exact `ExtractedRecord`, page and region that supported them. Foreign keys protect local record existence; services verify document/record/region tenant and scope agreement and that the source has not been quarantined or superseded.
- The original document, raw bytes and extracted values remain unchanged by reconciliation. Human acceptance, correction, rejection, and reason are explicit review decisions. A correction keeps the source value and unit alongside the corrected accepted value; the audit/change record identifies the actor, affected field/row, before/after digest or value, source and reason without copying sensitive raw document text into the governance ledger.
- `AuditLog` answers who was authorized to perform a mutation. `ChangeRecord` and numbered revisions answer what the domain record changed into and from. Both are written transactionally with the mutation; neither is a substitute for the original document.
- Derived operation/event projections are separate domain records linked to their originating report revision/activity, idempotent on promotion identity, and marked as report-derived. Approval does not silently rewrite or delete other projections. Reconciliation of a correction to already-promoted operational records is an explicit, audited action with conflicts surfaced to a human.

### 5. Server-side authorization, concurrency and retention

- Read, draft/edit, submit, review/approve, reconcile/import and export are distinct permissions/actions. The router declares permission dependencies; the service repeats organization/scope checks; action-level authorization is enforced server-side. UI visibility is never the authorization boundary.
- Create/import, transitions, corrections and exports support idempotency where retries could duplicate effects. Edits use compare-and-swap `edit_version`; transitions lock/check current state and revision in the same transaction. Concurrent edits or decisions fail as conflicts rather than last-write-wins.
- State changes, child replacement, `AuditLog`, `ChangeRecord`, idempotency completion, and any promotion/outbox write share a transaction. No public hard-delete route exists. Source documents and referenced revisions are retained; retirement/withdrawal is a governed state change subject to the organization's retention/legal-hold policy.
- A new table carries `org_id`, explicit indexes and uniqueness, relationships with deliberate `RESTRICT`/cascade behavior, and portable constraints usable on both SQLite and PostgreSQL. Any migration touching existing records must reject unexplained/ambiguous legacy values instead of guessing a repair.

### 6. Import and manual entry share one business lifecycle

- Manual and imported reports create the same logical report and draft revision, use the same typed validation and source/time/unit contracts, submit/review/approve through the same state machine, and render the same revision/export schema.
- Import is a proposal: extraction confidence, page/region evidence, rule-validation state, missing fields and conflicts are visible. Human reconciliation is field/row aware and distinguishes accept-as-extracted, correct, reject, and unresolved. Parsing, OCR, deterministic rules and high confidence do not equal human or engineering approval.
- Repeated identical imports are idempotent. A changed document for an existing report identity, an ambiguous shift/report number, stale revision, duplicate activity or incompatible asset scope is a visible conflict. No automatic approval or silent overwrite.

### 7. Survey azimuth frames and vertical datums are explicit provenance

- A survey azimuth declaration is the pair `(azimuth_reference, azimuth_reference_id)`. The type is `grid`, `true`, `magnetic`, or `unknown`; the ID is the exact named frame identity, not a type alias. Unknown types, missing identities, and differing pairs are not treated as compatible. Historical rows are not backfilled from the legacy free-form `magnetic_reference` field.
- Survey extraction records an explicit type stated in the azimuth heading or a controlled reference column, retains any exact frame-ID cell, and otherwise records `unknown`/`null` plus review flags. A human reviewer may add/correct the type, frame ID, or datum only from source evidence; the review decision is versioned and audited. `datum` is `rkb`, `msl`, `gl`, or `unknown` and is not assigned from a default during extraction.
- A trajectory has one declared common output azimuth frame and vertical datum. Each station retains the raw input azimuth, raw input reference type/ID, and any signed `grid_correction_deg`. A non-zero lateral tie-in must identify the same exact frame as the target trajectory. Unknown reference or datum values remain visible and cannot be used to establish plan/actual compatibility.
- The trajectory engine applies a correction only when the caller supplies the signed station correction and explicitly names a target **grid frame ID**. It does not derive magnetic declination or grid convergence. DDR promotion never applies a correction: rows carrying a correction stay in review until a separate explicitly targeted calculation path is used. Promotion batches require one exact frame pair and one explicit vertical datum. A later document can append only when both declarations exactly match the current trajectory; mismatches are held for review, never normalized or silently converted.
- Plan-vs-actual reconciliation requires known, equal vertical datums and exact equal azimuth type+ID pairs before comparing coordinates. Equal labels such as `grid` are insufficient if the frame IDs differ. Unknown/mismatched inputs produce no comparison offsets.

## CP83 survey-reference and trajectory governance

- Survey azimuths carry a controlled reference type (`grid`, `true`, `magnetic`, or `unknown`) and an exact operator/source-declared `azimuth_reference_id`. A type alone is not a frame identity. Missing, contradictory, unrecognized, or unlocatable declarations stay `unknown` and are not usable for trajectory calculations or cross-document promotion. Header-declared types cite the source header cell; row-declared frame identity, datum, azimuth and correction retain their own locators when present.
- The trajectory calculation requires explicit, mutually consistent known station frames. An optional output frame must be explicitly named by type and ID; converting into a named grid requires a finite signed `grid_correction_deg` for every converted station. The engine does not calculate magnetic declination or grid convergence. It retains each raw input azimuth, input frame identity, and signed correction alongside the effective calculation azimuth. True/magnetic or grid-to-true transformations are not inferred or supported.
- A vertical-section azimuth also requires an explicit reference type and exact ID matching the trajectory's output frame. A non-zero tie-in offset requires a declared frame identity matching the trajectory frame. The tie-in TVD is expressed in the parent trajectory's declared vertical datum; no separate datum transformation is attempted.
- The recognized vertical datum labels are `rkb`, `msl`, `gl`, `cf`, and `derrick_floor`. The literal `unknown` is preserved but is not compatible with another survey. Plan-versus-actual reconciliation requires exactly matching known vertical-datum values and exactly matching azimuth `(type, identity)` pairs before it compares any coordinates; mismatch returns no station deviations and an explicit violation. There is no implicit datum conversion.
- DDR promotion only accepts explicitly declared supported azimuth type/ID and vertical datum. It never applies a correction from the report. A station with a correction is held for human review because applying it requires an explicit target grid identity and a reviewed conversion decision. A batch with internal frame/datum differences, or a new batch that differs from the existing current trajectory, remains unpromoted. Exact matches may be appended; legacy rows with absent frame identity are not retroactively classified or joined. Retry/replay also verifies raw azimuth, frame, datum and correction provenance before reusing a promoted station.
- Migration `b83e4a6d1c29` adds nullable trajectory and raw-input frame columns. Existing rows are intentionally not backfilled: legacy `magnetic_reference` labels are not converted into reference types or exact IDs. New ORM trajectories default to `unknown`; imported trajectories retain source declarations with `validation.state = not_independently_validated` and `is_valid = false`. Context exposes the trajectory frame and per-station raw azimuth/correction provenance; DDR processing audit records declared survey frames.
- Migration `c79f2a61d5b3` adds explicit datum-origin and station-measurement-time provenance with database check constraints. Existing datum labels—including `rkb`—are classified as `legacy_unverified`, preserved verbatim, and marked in trajectory validation; no legacy datum origin is inferred. Existing station `measured_at` values are preserved in an audit snapshot, cleared from the trusted event-time field, and marked `legacy_unverified`. The downgrade preflights all rows before changing non-transactional SQLite DDL and refuses post-migration provenance or edited snapshots; a verified legacy-only downgrade restores the original values.
- A survey station receives an observed time only from its own timezone-aware ISO source cell. A report's period start/end or issue date does not become the station's measurement time. Missing, date-only, naïve, or malformed station timestamps stay unknown and retain their source locator/quality flag where present. Context exposes `observed_at` and applies station time filters only to `source_record` timestamps; legacy timestamps cannot satisfy a time-bounded query.
- Survey station depths are finite and non-negative, so a valid MD=0 surface station is retained. The minimum-curvature engine requires source-order MD to be strictly increasing and refuses duplicate or reordered stations instead of sorting them. DDR promotion requires internally consistent declared frames/datums, checks retries against the source payload and timestamp provenance, and only appends to a matching, explicitly source-captured trajectory with no calculated/stale state. Legacy/unverified, computed, ambiguous, overlapping, duplicate, or nonmonotonic append candidates are held for human review; azimuth corrections are never applied by document promotion.
- The bilingual extracted-record review guidance instructs operators to correct survey declarations only from cited source evidence, to keep unknowns unknown, and not to treat a correction as applied. Review remains versioned, tenant-scoped, permission-checked and audited; the UI payload editor stays LTR within Persian RTL layout.
- Software verification includes a separate multi-interval constant-curvature closed-form trajectory check, explicit correction/provenance tests, exact tie-in and vertical-section frame checks, twin mismatch refusal tests, promotion/replay tests, review validation, a data-preserving upgrade/downgrade migration test, and English/Persian review-direction tests. These checks do not validate the source declaration, field survey accuracy, survey-tool calibration, magnetic model, geodetic transformation, anti-collision uncertainty or qualified engineering acceptance. Operators commissioning imported survey data must obtain the frame type, exact frame identity and vertical datum from the source record; any conversion or source-quality acceptance requires an appropriately qualified owner and evidence recorded outside this software milestone.
